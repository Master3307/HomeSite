# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Personal website (home.master3307.org) built with Vite + React 19, plus several Node backends in `server/`: the Discord "Cultbot", a Discord OAuth account API, and a Discord profile/presence API. Package manager is **pnpm** (`packageManager` is pinned; CI uses Node 22 and `--frozen-lockfile`).

## Commands

```bash
pnpm install
pnpm dev            # builds search index, then Vite dev server; proxies /api -> http://127.0.0.1:3001 (discord-profile service)
pnpm build          # sitemap -> search index -> vite build -> export FDC polls into dist/ -> create dist/404.html
pnpm preview        # vite preview on port 8081
pnpm checks         # local equivalent of CI (scripts/checks.cjs); logs to .logs/
pnpm exec oxlint .  # lint only (config: .oxlintrc.json, react + oxc plugins)

# Setup (writes .env; guides, links, skip anything)
pnpm setup:gui      # local web page (Setup + Settings tabs), first free port 4780-4799, opens the browser
pnpm setup:cli      # same in the terminal
pnpm env:example    # regenerate .env.example from config/settings.cjs (checked by pnpm checks)

# Backends (each needs .env, see .env.example)
pnpm bot            # Discord bot (server/bot.cjs)
pnpm accounts       # Account/OAuth API (server/account-api.cjs, ACCOUNT_API_PORT, default 3002)
pnpm discord        # Discord profile/presence API (server/services/discord-profile.js, PORT, default 3001)
```

There is no test suite. Validation is `pnpm checks` (oxlint, `node --check` on every .js/.cjs/.mjs file, static bot-entry validation, build + dist checks). `pnpm checks --discord-smoke-test` additionally hits the live Discord API with credentials from `.env`.

Admin 2FA (run on the server): `pnpm 2fa:setup` (new secret into `.env` as `ADMIN_2FA_SECRET`, prints a terminal QR code and the key; `-- --force` replaces it), `pnpm 2fa:verify` (live code + countdown, any key stops), `pnpm 2fa:qr`, `pnpm 2fa:key`. `ADMIN_2FA=on` then requires a code for the admin login and critical actions (unlocking the hub / admin settings, export/import, .env changes and viewing). After a correct code the same login needs no new one for `ADMIN_2FA_GRACE_MINUTES` (default 10; `checkTwoFactor(code, purpose, holders)` with `account:<session>` / `hub:<id>` holders, browser side `src/lib/twoFactorGrace.js`). Logic in `server/services/totp.cjs`.

Hub (`/hub`, see Architecture): needs `HUB_KEY` (+ a 2FA code when `ADMIN_2FA=on`; with 2FA on, the admin key + code works too). The site owner (`DISCORD_USER_ID`) logged in on the site with Discord needs no key: with 2FA off that login is enough, with 2FA on only the code is asked. `HUB_TERMINAL=on` enables the server terminal.

Other scripts: `mail:test <address>` (checks the SMTP setup; `--all` sends the light/dark × English/German looks, `--preview <folder>` only writes the HTML), `bongo:import <folder>` (Bongo Cat assets from an AssetRipper export, see Bongo Cat below), `fdc:rebadge` (re-upload FDC option images to Discord with the number + emoji badge; preview by default, `--apply` / `--all`), `search:index` (rebuild `public/search-index.json`), `fdc:import` / `fdc:export` (FDC poll data), `sitemap`, `images`, `fonts:update` (self-hosted fonts: Google Sans Flex, the Material Symbols subset, and the JetBrains Mono Nerd Font for the hub console), `git-sync`, `cleaner`.

## Architecture

### Frontend (`src/`)
- `main.jsx` wraps the app in `HelmetProvider` → `BrowserRouter` → `AccountSettingsProvider` → `Root`.
- `Root.jsx` renders `App` plus the global `ThemeSwitch` / `LanguageSwitch`, and runs `twemoji.parse` over the whole tree on every route/language change (emoji served from `/twemoji/svg/`). `themeSwitchHiddenPaths` controls where the theme switch is hidden (glob-style patterns, e.g. `/cult*`).
- `App.jsx` holds all routes (`react-router` v8); unknown paths render `<Error forcedCode={404} />`. `scripts/create-404.cjs` turns the `<Route path>`s into `dist/serve.json` rewrites, so `pnpm serve` (no `-s`!) answers real routes with 200 and everything else with a real 404 (`dist/404.html`). Public routes that should be indexed must also be added to the hardcoded list in `scripts/generate-sitemap.mjs`.
- `pages/` are route components; `components/cult/` contains the Cult (Discord community) features: FDC archive/polls, voting, lobby code.
- Site search: `scripts/generate-search-index.mjs` crawls the routes in `App.jsx` and the components they render, collects static `t('key')` calls and resolves them in every locale into `public/search-index.json` (gitignored, generated). Each entry is identified as `<namespace>:<key>` with its source file:line. `components/Search.jsx` (ranking in `lib/search.js`) searches it client-side; `SearchHighlight` in `Root.jsx` scrolls to and highlights the hit after navigation. Profile search is a static placeholder in `lib/search.js`. Tune excluded routes/keys and per-route keywords in the script's config section.
- `lib/i18n.js` auto-discovers translations via `import.meta.glob('../locales/*/*.json')`: each folder under `src/locales/` is a language, each JSON file a namespace. Adding a language or namespace needs no code changes. Other languages are translated through Weblate.
- `/dash` (`pages/Dash.jsx`, `components/dash/`, `lib/dashSettings.js` version 2): look settings, editable search engines (the site's own ones too), and a board of widgets (`components/dash/widgets.jsx`: clock, bookmarks, site shortcuts, search box, iframe, note, weather via open-meteo, countdown, calendar, picture, status pings, custom JSON integration, sandboxed HTML) with an in-place edit mode. Its search is the site search (`components/Search.jsx` with `web` / `people` props): web engines, site pages, and for the owner Discord people via the hub. Synced in `settings_json.dash` (plain JSON up to 80 KB, `accountPrefs.cjs`). The custom CSS editor is `components/CssSettings.jsx`.
- `/card` setup in 3D (`components/setup/`): `SetupShowcase.jsx` (tabs, caption, zoom/reset buttons, the software tab as Plasma 6's "About this System" in the Info Center, Darkly + MateriaDark), `scene.js` (three.js viewer lit like a product shot: studio environment, soft key-light shadows on an invisible floor, neutral tone mapping; drag to turn, pinch or Ctrl + wheel to zoom while a plain wheel keeps scrolling the page; draws only while visible), `models.js` (every part built from its real size and product photos, 1 unit = 1 cm; shapes cut into an extrude must stay inside its outline or the hole isn't cut), `textures.js` (canvas-drawn markings, PCB, labels and the real desktop on the screens: top bar, centred dock, topography wallpaper, fastfetch with its own CachyOS logo). `cachyos.svg` is the official logo (from `cachyos-settings`, credited on /about). three.js (pinned) loads as its own chunk only when the section comes near. Phones: square stage, caption under it, tabs 3 × 2. Parts and facts: `SETUP` / `SOFTWARE` in `src/data/links.js` (versions from `kinfo` / `fastfetch`, update now and then), texts in `card.json` (`setup.*`).
- Frontend config: settings with `public: true` in `config/settings.cjs` are injected by `vite.config.js` and read via `src/lib/siteConfig.js` (needs a rebuild after changes). Never hardcode IDs, domains or URLs.
- Icons: Material Symbols are self-hosted as a subset font. Icon names used dynamically (`<Icon name={…} />`, `icon: '…'`) must be listed in `scripts/material-symbols.extra.json`, then run `pnpm fonts:update`.

### Backends (`server/`, mostly CommonJS `.cjs`)
- **Discord bot** (`bot.cjs`, based on NamVr's DiscordBot-Template): dynamically loads handlers from `events/`, `commands/<category>/` (legacy prefix commands), and `interactions/{slash,buttons,select-menus,context-menus,modals,autocomplete}/<category>/`. Adding a command means dropping a file in the right folder; follow the shape of existing files. Types live in `server/typings.d.ts`. CI statically checks that `bot.cjs` still references `DISCORD_BOT_TOKEN`, `DISCORD_CLIENT_ID` and `client.login(token)`.
- **Account API** (`account-api.cjs` + `services/discordOAuth.cjs`): Express on 127.0.0.1, Discord OAuth login, SQLite (`better-sqlite3`, `accounts.sqlite`), cached avatars. A reverse proxy routes public `/auth/*` and `/avatars/*` here.
- **Discord profile API** (`services/discord-profile.js` + `services/discord-profile/`): ESM Express service for presence/activity tracking, enrichment (RAWG/IGDB/SteamGridDB/Spotify), and the live-user routes. Public: `/`, `/health`, `/api/discord-profile/avatar` and `/<DISCORD_USER_ID>` (the home page card). Everything else that exposes people (`/<id>`, `/<id>-ui`, `/history`) needs the hub key or a hub login (`discord-profile/hub-auth.js`). This is the `/api` target in dev (`/profile-api` is the same without the prefix, for the `-ui` pages).
- **Hub** (`/hub`, `src/pages/Hub.jsx` + `src/components/hub/`; backend `services/hub.cjs` on the account API): overview/health/stats, member list + ranked search, live activity feed (SSE), running bot commands (`services/hubCommands.cjs` builds a stand-in interaction/message), logs (`services/hubLogs.cjs`), database/users/data files (`services/hubDb.cjs`), the settings workspace and a server terminal (`services/hubTerminal.cjs` + `pty-helper.py`, WebSocket with HTTP fallback, sessions resume after dropped connections; `components/hub/Console.jsx` handles touch itself: one-finger scroll with momentum, also inside full-screen programs, pinch for the text size, a typing field that sends each change live as a diff so phone keyboards' suggestions/autocorrect work, full screen sized to `visualViewport` above the on-screen keyboard, a text view for selecting output). Discord data comes from the bot's internal API (`services/hubBot.cjs`, `/hub/*` routes); the bot records every activity change for the Live tab in `db/hub-live.jsonl` (last 2000 events, max 7 days, not backed up). Login: `HUB_KEY` + 2FA → `__Secure-homesite_hub` cookie (parent domain, so the profile API's `-ui` pages accept it via `GET /hub/session`); sessions live in `db/hub-sessions.json` (not backed up). The code is public: keep every hub route behind `requireHub`, every mutation behind the Origin/CSRF check (`requireTrustedMutation`), log writes to the activity log, never send secrets to the browser.
- **Service logs:** every service calls `services/processLog.cjs` `capture(name)` first, which copies its console output to `.logs/services/<name>.log` (rotated at 5 MB). New services should do the same so `/hub` → Logs shows them.
- **Bongo Cat** (lobby cat, cat designer, designed FDC options): the game's textures from the owner's own copy, ripped with AssetRipper and imported via `pnpm bongo:import`, the setup stage "bongo", or the folder upload in Settings → Bongo Cat assets (`/admin-settings`, `/hub`). `shared/bongo-assets.mjs` holds the import rules (used by the browser upload and the server, no fixed item/theme lists: new items, slots, UI themes and `Icon_*` icons of a game update are picked up by importing again; slots the site draws are `SLOT_FILES`). `services/bongoAssets.cjs` installs atomically into `db/bongo-cat/` (`textures/`, `catalog.json` with items, aliases, layer bounds, UI themes cut from the `sactx-*` sheets into `ui-<theme>-<Piece>.png` plus a colour palette per theme that the site's own layout is drawn in, the game's fonts from `Assets/Font` (`catalog.fonts`; Nunito and Noto Sans are used as "Bongo Nunito" / "Bongo Noto Sans" in the Bongo UI and on /cult once imported), hashes, history); updates only replace changed files and keep retired items. `shared/bongo-design.mjs` is the layer stack (part offsets taken from the game's scene: bongos lower and in front, hat above; cats face right, `flip` mirrors) + the FDC design layout (`{ cats: [...] }`, 1-4 cats, every slot combination a GIF frame), shared by the browser preview and `services/bongoRender.cjs` (PNG/GIF). Search words: curated single words in `shared/bongo-aliases.json` (baked in at import and joined again when the catalog is served), plus words FDC editors add in the picker (right-click) in `db/bongo-aliases.json` (backed up, merged on import; edits are queued so quick changes don't overwrite each other). Routes in `services/bongoWeb.cjs` (catalog, textures, per-user favourites + UI theme in `db/bongo-favorites.json`, lobby wardrobe, admin import); lobby style/wardrobe/winner logic in `services/lobbyStyle.cjs` (`db/lobby-cat-style.json`). Without imported assets the lobby cat is hidden and FDC options need an image; with them every new option needs a design (`option.design`, `option.display`, file `<n>-design.png|gif`).
- **Members & privacy** (`/cult/user/:key` with `@username` | Discord ID | account id, `/cult/settings`, `/cult/members`, `/cult/privacy`): `services/members.cjs` (account API: profiles, public/private, bongo avatars + uploaded background picture/GIF, per-user presets, member list, reports into the review channel, nickname changes via the bot, lobby cat taps, deleting an account + the daily cleanup of people who left `ACCOUNT_INACTIVE_DAYS` ago) and `services/memberData.cjs` (bot, internal API `/members/*`, `/privacy/forget`: Discord data for profiles, presence, reports, nickname, erasing a user from the bot's data + its messages that mention them). `services/privacy.cjs` is the shared `db/privacy.json` (private profiles never shown online, deleted accounts hidden from every lookup for 13 days, salted hashes so a restored backup can't bring them back; backup.cjs skips/scrubs them). Deleting rewrites the activity log once (`activity.forget`), leaving a single "deleted their account" entry. Login is members-only (`MEMBERS_ONLY_LOGIN`). Bongo avatars: `shared/bongo-avatar.mjs` (free layers, snap, rotate) rendered by `bongoRender.renderAvatar`. Settings sync in `users.settings_json` (`services/accountPrefs.cjs`, client `src/lib/prefs.js` + `accountSettings.jsx`). **Keep `src/pages/CultPrivacy.jsx` in sync with what is stored.**
- **Admin settings = hub Settings:** `/admin-settings` forwards to `/hub/settings` when `HUB_KEY` is set (backups, Bongo Cat assets, every .env setting); without it the old page still works for a fresh server. `adminBackup.cjs` accepts an unlocked hub session (`hubSessionOf`) like an unlocked admin page.
- **Profile answers & birthdays:** the onboarding roles (`PROFILE_ROLE_ID`, `PROFILE_GENDER_ROLES`, `PROFILE_HOBBY_ROLES`) move into the site profile for everyone with an account: the bot (`services/profileRoles.cjs`) watches role changes, sweeps every 10 minutes and runs on account creation, posts to `POST /internal/profile-roles` (members.cjs) and removes the roles. Options in `shared/profile-options.json`, UI `src/components/cult/AboutMe.jsx`. Birthdays: `services/birthday.cjs` is the shared store (bot `/birthday` and the site), with `setAt` (first saved = priority when two celebrations fall on one day; the later one moves a day, `celebrations(year)`), `changedAt` (one change per 6 months, `CHANGE_LOCK_MS`) and the birthday person's `dressCode`. Website routes in `services/birthdaysWeb.cjs` (`/cult/birthdays`, profile line, `/cult` banner, the lobby cat wears the dress code: `lobbyStyle.cjs` order temporary > birthday > FDC winner > mode). The birthday dress code is picked on the celebration day itself (`dressCode.for`, `currentDressCode`), cleared the day after. The list shows logged-in members everyone with a birthday (no account: Discord name + user card, `members.discordUsers`). Reminders `services/birthdayReminders.cjs` (`db/birthday-reminders.json`, DMs from `birthdayCelebrations.cjs` the day before and on the day); dress code pictures in `db/birthday-dress/`.
- **FDC migration:** new options are designed cats only (the "Image + cat" mode is gone; without imported assets options stay pictures). Recycling-bin items carry a design (`item.design`, rendered into `recycling-bin/designs/`); picture-only items show a red "!" and are designed next to their old picture (`DesignEditor` `reference`). `?fdc=migrate` (`FdcMigration.jsx`, `services/fdcMigration.cjs`) covers every option with a picture but no design: archived and running poll options (`p.<date>.<n>`, saved through the bot's `setDesigns`, the option then shows the design and keeps its picture) and bin items whose FDC is gone (`b.<id>`); a bin copy of an archived option is designed together with it. Editors design directly, members suggest (`recycling-bin/suggestions.json`), editors approve / adjust / reject; the button disappears when nothing is left. With the Bongo Cat assets imported, pictures are retired everywhere (create, manage, past FDCs by hand): fdcWeb rejects new / changed images, removing a design or switching back to the picture; editors see a small red "!" on picture-only options and FDCs and migrate them in the manage view (old picture faded behind the slot, side by side in the designer). Design model (version 3, `shared/bongo-design.mjs`): per cat `skins/hats/bongos` picks mixed by `combine` (all | paired), fixed looks `outfits` that never mix, `link` (changes in step with the cat before it); `mix` across cats each | together | all | shuffle (version 2 designs keep "all"), `frameMs`, `tap` ({ on, ms }).
- **Email look** (`services/mailTemplate.cjs`): every email is a tiny cult page in the member's language (`src/locales/<lang>/email.json`), theme (light / dark / system → the mail app's mode), accent and custom CSS, with the seasonal logo inline (cid, `shared/seasons.json`). Notifications carry `List-Unsubscribe` + one-click (`services/emailUnsubscribe.cjs`, signed links, exempt from the CSRF check); security emails (new browser, password/2FA changes) always go out with a reset link (`/cult?login=reset&email=`).
- **Email login & 2FA** (`services/emailAuth.cjs`, `services/mail.cjs`): accounts are only created with Discord; a verified email + password is an extra way in, with optional second factors (email code, authenticator app, passkeys via SimpleWebAuthn). Needs the `SMTP_*` settings (`pnpm mail:test you@example.com`). Discord logins never ask for these factors; "Trust this browser" skips the second step for 30 days (`__Secure-homesite_trust`, MAC over the password hash + methods). Codes are HMACs, TOTP secrets AES-GCM sealed with the internal key; the hub DB view masks credential columns.
- Other `services/` modules (levels, birthday wishes, petting, sticky messages, Minecraft status, FDC archive, DM forwarder) are used by the bot.
- Runtime data is stored in `server/services/db/` (gitignored). FDC poll data in `server/services/db/fdc-polls` is exported to `public/fdc-polls` (dev) or `dist/fdc-polls` (build) by `scripts/export-fdc.cjs`.

### Deployment
`scripts/deploy.sh` runs on the server (`/opt/homesite-api`): hard-reset to `origin/master`, `pnpm install --frozen-lockfile`, `pnpm checks`, `pnpm build`, then restart the systemd units `homesite`, `accounts-api`, `discord-bot`, `discord-profile`. It is triggered by `server/services/github-deploy-listener.mjs`. So `master` is production; day-to-day work happens on `dev`.

### Backups (keep up to date!)
`server/services/backup.cjs` (admin page `/admin-settings`, also the Settings tab in `/hub`; `/backup` redirects there; routes in `server/services/adminBackup.cjs`) exports everything git doesn't track — `server/services/db/` (accounts SQLite, FDC archive, recycling bin, activity log, bot data), avatars, logs, `.env` — as one encrypted archive and imports it again (merge or restore).
- **Any change to runtime data must be checked against the backup immediately:** new files or folders written at runtime, new SQLite tables/columns, renamed paths or changed JSON/CSV formats. Make sure they are included (or deliberately listed in `EXCLUDED`), and that imports merge them correctly (`MERGERS` for files with per-user data such as points, levels, birthdays; `mergeAccounts` for the database).
- Compatibility both ways: an old backup must import into new code and a new backup into old code (column intersection, tolerant JSON readers, `manifest.version`).

### Settings / environment variables (keep up to date!)
`config/settings.cjs` is the single source of truth for every .env setting (section, feature, label, description, type, importance, `needed`, default, `public`, `applies`, help links). It drives `.env.example` (`pnpm env:example`), `/admin-settings`, the hub's Settings tab, `pnpm setup:gui` / `setup:cli` (stages in `scripts/setup/stages.cjs`) and runtime defaults (`server/config.cjs`: `setting`, `ids`, `number`, `enabled`, `origin`).
Whenever a setting is added, renamed, removed or changes meaning:
- Add/update it in `config/settings.cjs`, run `pnpm env:example`, and add it to a setup stage if a newcomer should be asked about it.
- Read it through `server/config.cjs` / `siteConfig`, never `process.env` with a personal hardcoded fallback. Empty optional values must switch that feature off cleanly, not crash.
- Owner-specific values (IDs, domains) belong in the local `.env`, not in code or `.env.example`.

## Conventions
- Conventional Commits (`feat:`, `fix:`, `chore:`, `refactor:`, `docs:`, optional scope, `!` / `BREAKING CHANGE:` for breaking changes). See `.github/.copilot-commit-message-instructions.md`.
- Branch prefixes: `feat/`, `fix/`, `docs/`, `refactor/`, `test/`, `chore/`; PRs target `master`.
- Never commit `.env`; document new env vars in `.env.example`.
- Commit messages and PR descriptions must not include a `Claude-Session:` trailer or session link unless the owner explicitly asks for it.
